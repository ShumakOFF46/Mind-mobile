═══════════════════════════════════════════════════════════
1. НИКАКИХ файлов размером более 300-400 строк. Разрастающуюся логику разбивай на модули/виджеты/notifier'ы по фичам.
2. Никакого "спагетти-кода", вложенности более 3 уровней или смешивания слоёв (UI-логика внутри API-вызовов, прямые `dio.get()` из виджетов вместо `api_client.dart`).
3. Никаких захардкоженных секретов, base URL бэкенда или API-ключей в коде — только через конфиг/окружение сборки.
4. Не генерируй весь файл целиком, если изменилась одна функция/метод. Предоставляй точные diff-ы или чётко указывай, какой файл и какую часть менять.
5. Не предполагай формат ответа `routers/chat.py` (Lab-контракт, единый JSON `{content, blocks, conversation_id}`). Твой контракт — SSE `routers/app_chat.py`: `{content}` чанками → опционально `{calendar_proposal}` → `{conversation_id}` → `[DONE]`. Роутер ещё не мигрирован на общий `chat_engine.py` — не меняй ожидания клиента заранее.
6. Никогда не интерпретируй свободный текст пользователя как safety-критичный ответ (`restriction:*`, `symptom:*`) на клиенте. Такие вопросы — только структурированный тап по кнопкам (`tri_state`/`enum`/`multi_enum`), отправляется ровно значение из `options`, не текст.

═══════════════════════════════════════════════════════════
🏛️ АРХИТЕКТУРНЫЕ ПРИНЦИПЫ (ООП и Модульность)
═══════════════════════════════════════════════════════════
- Single Responsibility Principle: один widget/notifier/repository — одна ответственность.
- Dependency Injection: через Riverpod Providers, никаких зависимостей, создаваемых внутри классов напрямую.
- Interface Segregation: абстракции для SDUI-рендерера (factory/switch по `block.type`) и для API-клиента, чтобы новый тип блока не требовал правки несвязанных мест.
- Feature-first структура (`features/{auth,chat,calendar,profile}/...`), общая логика между Beauty/Nutrition/Fitness выносится в переиспользуемый core-слой, а не копируется.

═══════════════════════════════════════════════════════════
💻 ПРАВИЛА ПО СТЕКУ ТЕХНОЛОГИЙ
═══════════════════════════════════════════════════════════

[1. FLUTTER / DART]
- State Management: строго Riverpod (Providers, Notifiers) — никаких мутируемых глобальных синглтонов.
- Навигация: `go_router` с декларативной конфигурацией маршрутов.
- Сетевые запросы: `Dio` с интерсепторами токенов и обработки ошибок, все вызовы — только через `api_client.dart`.
- Архитектура: feature-first / Clean Architecture; переиспользуй общий core-слой между Beauty/Nutrition/Fitness точками входа.

[2. SERVER-DRIVEN UI]
- Рендер JSON-блоков от бэкенда — через factory/switch-паттерн, маппинг `block.type` → Flutter-виджет, строго по `contracts/sdui_blocks/*.schema.json`, не по фактическому ответу бэкенда в моменте (схема может опережать текущую реализацию).
- Неизвестный `block.type` → `UnknownBlock` с graceful fallback (нейтральный виджет + лог), приложение не должно падать/зависать.
- `calendar_proposal` — существующий блок, переиспользуется для флоу планирования (не создаётся параллельный виджет); выбор слота — только структурированный тап, без парсинга дат из текста.
- Вопросы анкеты с `input_mode: "buttons"` — кнопки `tri_state`/`enum`/`multi_enum`; с `input_mode: "free_text"` — обычное текстовое сообщение в чат, интерпретация (`certainty`) происходит асинхронно на бэкенде, не на клиенте.

[3. СЕТЬ И МЕДИА]
- Фото (`uploadPhoto`) — передавать `conversation_id`, когда он есть в контексте чата и когда соответствующий бэкенд-эндпоинт его принимает; не имитировать эту связь раньше, чем контракт это подтвердит.
- Медиа — только по presigned URL, полученным от бэкенда, без собственного кеширования как «источника правды».

[4. МУЛЬТИЯЗЫЧНОСТЬ И ЛОКАЛИЗАЦИЯ (i18n)]
- Все строки UI — через систему локализации (`intl`/`slang`). Никаких захардкоженных строк на русском (или любом другом) языке в Dart-коде, включая служебные подписи кнопок (`Да`/`Нет`/`Не уверена`) — это ключи локализации, соответствующие `options_labels`/`label` из схемы вопроса.
- Единицы измерения по умолчанию — метрические (кг, см, ккал, мл), синхронно с бэкенд-конвенцией; имперская система — только вслед за явным выбором пользователя, с сохранением последовательности в рамках сессии.
- Терминология доменов (Beauty/Nutrition/Fitness) — профессиональная и культурно адаптированная под целевой язык, без калек с английского там, где есть устоявшийся термин.
